DistServe 읽어보기

Created on November 21, 2026

2026   ·   llm   inference   paper-review   ·   paper-review

정말 오랜만에 논문을 읽어본다. 회사 업무 상 추론 최적화를 많이 한다고 하고 있는데, 계속 vision 관련된 최적화만 해왔지, LLM이나 트랜스포머 계열에 대한 최적화는 경험이 뭐 거의 전무하기 때문에 이러면 안되겠다 싶어서 핫하다는 추론 최적화 관련 논문 학회의 최근 3년간의 베스트 3 페이퍼(또는 영향력 있는 페이퍼)들을 찾아봤고, 그것들 중에 하나가 지금 소개할 DistServe이다.

DistServe는 LLM 모델을 최적으로 서빙하기 위한 하드웨어 인프라를 어떻게 구성해야 최적의 효율을 낼수 있는지에 대해서 이야기하고 있다. 가장 중요한 개념으로는 프리필과 디코딩 과정을 나누는 것이다.

프리필과 디코딩 과정을 나누기

LLM 추론의 과정은 크기 프리필과 디코딩으로 나뉜다. 프리필은 나의 프롬프트를 LLM 모델로 실행하는 과정이고, 디코딩은 나의 프롬프트를 해석한 기반으로 출력 토큰을 생성해나가는 과정이다. 이 과정에 대해서 내가 몇 가지 잘못 이해하고 있었던 기본 개념이 있었는데…

a) 프리필과 디코딩은 같은 weight을 사용한다.

프리필과 디코딩은 같은 weight을 사용한다고 한다. 난 처음엔 이게 인코더/디코더로 나뉜 개념이라고 생각했어서, 각각 weight도 layer수도 다를 수 있다고 생각했는데, 아니다. 같은 weight을 사용하기 때문에 자연스럽게 레이어 수도 같을 수 밖에 없다. 그냥 똑같은 모델이니까.

b) 프리필과 디코딩의 차이는?

프리필은 나의 프롬프트를 LLM 모델로 실행하는 과정이라고 위에서 말했다. 이 때 내 프롬프트 전체를 실행시킨다. 내 프롬프트가 100개 토큰으로 구성되어 있으면 100개를 한꺼번에 돌린다는 것이다. 물론이게 실제로는 Chunk 개념으로 나뉘어 돌게 될 것이다.

반면 디코딩은 토큰을 하나 하나 생성한다. 3개의 토큰을 생성한다고 하면, 3개를 하나, 하나, 하나씩 생성한다.

c) 프리필과 디코딩의 서버 구성

여러 GPU에 모델 로딩해서 프리필 용으로 사용할 수 있다. 디코딩 역시 마찬가지로 여러 GPU에 로딩해서 디코딩 용으로 사용할 수 있다. 꼭 한 대로만 모델을 로딩한다고 생각하지 말자.

d) KV-Cache 연산 방법

KV-Cache가 어떻게 동작하는지 내가 잘 모르고 있었다. 프리필 과정에서는 재사용되는 Key, Value 없이 모두 일일이 계산한다. 프리필 과정에서 각 레이어에서 어텐션 연산을 할 때 Key와 Value 값을 레이어마다 저장한다. 그리고 디코딩 과정에서 ① 각 레이어의 연산을 진행할 때 지난 프리필 과정에서 저장해뒀던 Key, Value 값을 다시 사용한다. 그리고 ② 다음 토큰을 만드는 어텐션 연산을 실행하면서 생성된 Key, Value를 기존의 Key, Value에 업데이트한다. ①과 ②를 반복하여 계속 출력 토큰을 생성해낸다.

e) 노드와 클러스터

노드는 GPU가 여러 개 달려있는 서버를 의미하고, 이런 노드들이 여러 개 묶여 있는 걸 클러스터라고 한다.

DistServe에서는 프리필과 디코딩 과정의 연산 특성이 다르기 때문에 두 과정을 서로 다른 GPU에서 실행시키면 GPU 사용율을 최대한으로 끌어올릴 수 있다고 한다. 그런데 시작부터 뭔가 이상하지 않나?

“프리필이랑 디코딩이랑 같은 모델이잖아? 그걸 서로 다른 GPU에 올려? 그럼 GPU도 여러 개여야 하잖아? 여러 개 GPU 쓰면 뭐 당연히 더 빨라지겠지”

눈치 빠른 사람들이라면 여기에서 눈치챘을 것이다. DistServe의 전제 조건은 노드, 즉 여러 개의 GPU를 이용하는 서버 혹은 그런 노드 서버들의 묶음인 클러스터 단위를 전제로 이야기하는 것이다. 단일 GPU에서도 실행시킬 수 있을만한 아주 작은 크기의 모델을(예를 들어 1B) 최적화하겠다는 것이 아니다.

프리필과 디코딩의 연산적 특성

프리필과 디코딩의 연산적 특성을 이해하고 있으면 이 논문을 아주 무난하게 이해할 수 있다.

a) 프리필의 연산 특성

compute-bound 이다. 프리필은 연산량이 중요한 과정이다. 프리필의 연산을 최적화하기 위해 tensor parallel과 pipeline parallel 두 가지의 병렬처리를 할 수 있다.

tensor parallel은 모델이 로딩될 때, 하나의 레이어가 여러 GPU에 분산되어 로딩되어 추론 시에도 하나의 레이어를 추론할 때 여러 GPU에서 연산을 나누어 실행하게 된다. 이 때 서로 다른 GPU에서 실행한 결과 값을 한 곳에 모으는 Gather 작업 등이 필요한데, 이런 작업이 tensor parallel의 대표적인 오버헤드라고 볼 수 있다.(논문에서는 intra-op로 표현)

pipeline parallel은 모델이 로딩될 때 여러 GPU에 분산되어 로딩되는 것은 똑같은데, 레이어 단위로 쪼개진다. 전체 레이어가 8개이고 GPU가 2개라고 하면, 0~3번 레이어는 GPU-0에 로딩하고 나머지 4~7번 레이어는 GPU-1에 로딩하는 것이다. 이렇게 하면 하나의 추론이 실행될 때 0~3번 레이어를 끝낸 결과가 GPU-1로 넘어가서 나머지 4~7번 레이어를 GPU-1에서 실행하게 된다. 이렇게 하면 GPU-1에서 연산하고 있을 때 GPU-0은 다른 요청의 앞부분을 실행할 수 있게 된다. (논문에서는 inter-op로 표현)

b) 디코딩 연산의 특성

memory-bound 이다. 디코딩은 토큰을 하나 생성하는 과정이라서 연산량 자체가 엄청 많지 않다. KV-Cache를 함께 사용하면 디코딩 시 레이어마다 Key, Value 값을 재계산하지 않고 메모리에 있는 값을 재사용할 수 있다. 따라서 연산량이 많은 것은 아니지만, 메모리에서 Key, Value 값들이 자주 이동하기 때문에 메모리의 입출력에서 시간이 많이 소요된다.

추론에 대한 성능은 goodput으로 측정한다.

DistServe에서 추론의 성능은 goodput으로 측정하고 있다. goodput이 무엇이냐?

“TTFT와 TPOT에 대한 SLO를 모두 만족시키는 요청이 전체 요청의 90% 이상일 경우, GPU 1장에서의 초당 요청 수”

처음 보는 사람이라면 조금 복잡하게 느껴질 수 있는 개념이다. 그런데 이거 생각해보면 매우 상식적인 메트릭이다. TTFT(Time To First Token)은 프리필 과정의 소요시간(latency)를 의미한다. TPOT는 디코딩 시 하나의 토큰을 생성하는데 드는 시간(latency)이다. TTFT와 TPOT 각각 SLO가 있을텐데, DistServe에서는 프리필과 디코딩을 나눈다고 했기 때문에 프리필 과정과 디코딩 과정의 SLO를 각각 관리할 수 있다. 따라서 전체 요청에 대한 프리필을 하고 있는 GPU와 디코딩을 하고 있는 GPU의 SLO를 측정할 수 있고, 두 SLO를 모두 만족하는 경우가 전체 요청의 90% 이상일 때, 하나의 GPU가 도대체 몇 개의 요청을 1초에 처리하냐?(Throughput)

인프라 환경을 크게 두 가지로 나뉜다.

DistServe에서는 노드와 클러스터의 하드웨어에 따라서 두 가지로 나눈다.

a) high node-affinity 클러스터

노드와 노드가 infiniband로 연결되어 있는 클러스터를 말한다. infiniband는 서버와 서버간에 데이터를 빠르게 주고 받기 위한 네트워크 기술이다. Infiniband도 세대 별로 속도가 다른데, 예를 들어 XDR의 경우 100GB/s 정도의 속도가 나온다. 모델의 KV-Cache 크기가 2G~3G씩 된다고 하더라도 100GB/s면 데이터 이동 소요 시간이 무시할 수 있을 정도이다. (물론 100GB/s는 이론 속도이다)

[그림2] InfiniBand 케이블
b) low node-affinity 클러스터

노드와 노드가 infiniband가 아닌 상대적으로 느린 네트워크를 통해 연결되어 있는 클러스터를 말한다. 이런 환경에서 2GB ~ 3GB 정도 해당하는 KV-Cache가 이동하려고 하면 오래걸린다. 이런 환경에서는 노드와 노드 사이에서 KV-Cache가 이동하도록 구성하면 안된다.

low, high node-affinity에 관계없이 NVLINK는 가정하고 있다. 하나의 노드 안에서 GPU끼리는 NVLINK로 이어져 있는 것으로 가정한다는 말이다. NVLINK는 GPU 마다 다르지만 Amphere, Hopper 기준으로는 50GB/s, Blackwell, Rubin 기준으로는 100GB/s 정도의 속도를 보인다고 한다.

두 가지 환경에 대해서 서로 다른 알고리즘을 제안한다.

DistServe에서 high node-affinity와 low node-affinity 환경에 대하여 서로 다른 알고리즘을 제안한다. 여기서 말하는 알고리즘은 프리필/디코딩을 어떤 노드에 GPU 몇 개로 구성해야 최대 goodput이 나오는지를 구하는 알고리즘이다.

a) high node-affinity 클러스터에 대한 알고리즘(알고리즘1)

Infiniband를 가정한 환경이기 때문에 조금 쉽게 구성할 수 있다. inter-op와 intra-op를 조합해서 각 조합마다 모델을 로딩할 수 있는지 보고, goodput을 비교하는 과정을 반복해서 최종적으로 마지막에 최고의 goodput을 내는 인프라 조합을 찾아낸다.

[그림3] High node-affinity 클러스터 구성에서의 prefill/decoding 구성과 연산 처리 흐름

위 그림에서 3번 과정에서 KV Cache가 다른 노드로 전송된다. InfiniBand에서는 KV Cache를 보내는 것도 무시할 수준의 영향이라는 판단이다.

b) low node-affinity 클러스터에 대한 알고리즘(알고리즘2)

low node affinity, 즉 노드들끼리의 유연함이 적은 환경에서의 클러스터 구성을 위한 핵심 아이디어로 서로 쌍이 되는 프리필과 디코딩 과정을 노드 단위로 묶어 버리는 것이다. 예를 들어서 아래와 같이 구성할 수 있다.

왜 위와 같이 구성할까? 보면, 같은 층의 범위에 해당하는 프리필과 디코딩이 하나의 노드에 존재하고 있다. 이렇게 두는 이유는 프리필 과정에서 계산된 KV-Cache 값이 다른 노드를 넘어갈 필요가 없도록 구성하기 위함이다. low node affinity 노드에 대해서도 NVLINK는 있다고 전제하고 있기 때문에 KV-Cache 값이 같은 노드에서는 빠른 속도로 이동할 수 있다.

구현 방법 및 실험

DistServe의 구현은 Swift Transformer를 기반으로 작성했다고 한다. Swift Transformer는 FlashAttention, Continuous Batching, PagedAttention 등을 지원하는 C++ 기반의 트랜스포머 인퍼런스 라이브러리이다.

실험 환경은 다음과 같다.

  • 클러스터: 1개
  • 노드 수: 4개
  • 노드 당 GPU 수: 8개 (총 32개 GPU)
  • GPU: Nvidia SXM A100 80GB GPU (NVLink connected)
  • cross-node 대역폭: 25Gbps (3.3GB/s)
  • 모델: OPT-13B, OPT-66B, OPT-175B

현재의 vLLM과 비교한다면…

위 결과를 그대로 보고, vLLM 별로네~ 이러면 안된다. 위 논문에서의 vLLM은 거의 초창기 버전인 v0.1.x ~ v0.2.x 버전이라고 한다. 이후 vLLM에서 cuda graph, chunked prefill 등등 각종 최적화 테크닉이 적용되고 있다고 하고, 사실 DistServe에서 핵심이 prefill과 decoding을 분리하고 나름의 알고리즘을 통해 최적의 GPU/노드 할당을 하는 건데, 사실 그 구성 그대로 vLLM에서 하면 될거 같다. 논문의 Github를 보면 DistServe의 기반은 Swift Transformer 기반이라고 한다.

진짜 오랜만에 논문 하나 봤는데, 앞으로 LLM 쪽으로 추론 최적화 공부할 것들이 엄청 많이 보인다.
